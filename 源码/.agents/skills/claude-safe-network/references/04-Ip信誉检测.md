# 04 · IP 信誉检测（能力与边界）

> 这一章解决一个具体问题：**"我这个出口 IP 到底干不干净？"**
> 内容全部来自本机实测（2026-09-13），不是照抄网站说明。
>
> **2026-09-13 更新（重要）**：早期版本判定"只有 iprisk.top 能自动化，其余三个必须人工"。
> 后来发现**无头 Chrome 可以真实执行 JS** —— 只要给它真实 UA、独立 `--user-data-dir`
> 和 `--virtual-time-budget`，`ping0.cc` 与 `ip.net.coffee/claude/` 都能拿到完整渲染后的值。
> 所以现在**四个站里只有一个（ippure.com）还必须人工看**，原因是它要求一个混淆 JS
> 现场算出的 `x-t` 签名头，而不是渲染问题。
>
> 教训：**"抓不到"往往不是站点的限制，而是抓取姿势不对。** 详见第 2 节。

---

## 1. 五个检测入口的可测性矩阵

| 入口 | 无头可测？ | 本套件怎么处理 | 拿到什么 |
|---|---|---|---|
| `cloudflare.com/cdn-cgi/trace` | ✅ 纯文本，无任何反爬 | `Check-ClaudeIp.ps1` 主手段，逐入口跑 | `ip` / `loc` / `colo` / `warp` / `tls` |
| `claude.ai/cdn-cgi/trace` | ✅ 纯文本 | 同上（证明 claude.ai 也由 Cloudflare 前置） | 同上 |
| `iprisk.top` | ✅ 服务端渲染 | `Check-IpReputation.ps1` | 纯净度评分 / IP 类型 / 是否代理 / 是否机房 / 标签 / 风险项 |
| `www.ping0.cc` | ✅ **真实渲染可测** | `Check-IpReputation.ps1`（`Invoke-HeadlessDomFetch`） | 风控值 % / 等级标签 / IP 类型 / 原生 IP / 共享人数 / ASN 摘要 |
| `ip.net.coffee/claude/` | ✅ **真实渲染可测** | `Check-ClaudeIp.ps1`（`Invoke-HeadlessDomFetch`） | 专向出口 IP / Trust Score / IP 属性 / VPN·Proxy·Tor·Crawler / 滥用记录 / 支持地区 |
| `ippure.com` | ❌ 不可测 | 只能人工看，必须用**专用 Chrome** | 人机流量占比 / IP 来源属性 / 系数 |

**一句话记法**：`iprisk` / `ping0` / `ip.net.coffee` 三个都能自动出结论；
只有 `ippure.com` 必须人工，因为它的门槛是**签名算法**而不是**渲染**。

## 2. 为什么现在只剩 `ippure.com` 必须人工（根因，不是玄学）

### 2.1 `ippure.com` —— 需要 JS 生成的签名头

- 数据接口是 `api.123169.xyz/api/info/ip-basic/<IP>`。
- 直接请求（哪怕带 `Origin` / `Referer`）返回 `{"ok":false}`。
- 站点前端脚本 `security.C1jHOmoV.js` 里有 `headers.get("x-t")` 与 `defaultOrigin: "https://api.123169.xyz"`。
- 也就是说请求必须带一个**由混淆 JS 现场算出来的 `x-t` 签名头**。用 curl / 无头抓取复现这套签名没有稳定收益。
- **结论**：不要试图绕过。用专用 Chrome 人工看。

### 2.2 `ping0.cc` —— 踩过两个坑：抓取姿势 + 站点按出口 IP 限流

**坑 1（姿势）**：首次 `GET` 能拿到约 147 KB 带数据的 HTML；用无头 Chrome 却稳定吐 41 字节空页。
根因是**无头默认 UA 里的 `HeadlessChrome` 字样**被站点识别。修好两件事后，
同一台机器每次都能稳定拿到 113 KB 完整渲染页：

1. **换成真实 Chrome UA**（从本机 `chrome.exe` 的 `ProductVersion` 现取主版本，实测 149）
   —— 换成真实 UA 后，**同一秒**就能拿到完整页；不改 UA 则稳定吐 41 字节空页。
2. **加 `--disable-blink-features=AutomationControlled`** —— 抹掉 `navigator.webdriver` 特征。

**坑 2（限流，真实存在，别再自我安慰）**：姿势全对之后，**短时间内反复自动访问同一出口 IP**
仍然会换来约 1.4 KB 的 Cloudflare Turnstile 挑战页
（含 `cf-turnstile`、`data-sitekey="0x4AAAAAAB01fdNepRQppzkd"`、`AliyunCaptchaConfig`）。
为此专门做过对照实验：把 UA / `--user-data-dir` / `--virtual-time-budget` 全部换成长效持久 profile
（cookie 保留、UA 真实）后重试 —— **依然被拦**；同一轮里 `ip.net.coffee` 却完全正常（`Trust Score=100`）。
→ 结论：**这是 Cloudflare 边缘按出口 IP 计的临时限流，与本机配置、UA、cookie 都无关。**

**本套件的应对**（不是假装成功）：`Test-CaptchaGate` 识别挑战页特征 → 自动重试 1 次（间隔 5 秒）
→ 仍失败则如实报 **`[WARN]`** 并写清原因，**绝不拿空页冒充合格**。
恢复办法只有两条：**隔一段时间再跑**，或 `-OpenBrowser` 用浏览器人眼复核一遍。
⚠️ 排查期间**不要连续手跑 ping0 探测** —— 那只会延长限流。

> 所以 `Test-CaptchaGate` 现在只作为**兜底**：真被拦下时才报 `[WARN]`，
> 正常路径下它一次都不会触发。

### 2.3 `ip.net.coffee/claude/` —— 早期误判为"数据不在 HTML 里"，实为没等 JS 跑完

**早期结论（已推翻）**：无头抓取能拿到约 89 KB HTML（HTTP 200），但页面里没有 IP 值；
全站 grep 只得标签词（`机房`、`住宅`、`风控`、`原生`、`ASN`），都是模板文案。
于是当时判断"数据完全由客户端 JS 注入 → 抓来的 HTML 里没有答案 → 只能人工看"。

**真相**：它是 SPA，数据确实是 JS 注入的，但只要**等 JS 跑完**（`--virtual-time-budget=8000`）
再 `--dump-dom`，值就全在里面了 —— 实测拿到 93 KB 完整 DOM，
`Claude AI出口IP <出口IP>` / `Trust Score 100` / `家庭住宅IP` 全部可解析。

**唯一真正的例外是 `ippure.com`（见 2.1）**，因为它要一个混淆 JS 现算的 `x-t` 签名头 ——
那是**算法门槛**，换任何抓取姿势都没用。

## 3. 可自动化的部分：怎么做的

### 3.1 Cloudflare trace（判"出口 IP 与落地国家"）

这是**最可靠的自动化手段**，因为它返回纯文本 key=value，没有任何反爬。

```powershell
# 裸跑（走 TUN）
curl.exe -s https://www.cloudflare.com/cdn-cgi/trace

# 走某个专用入口
curl.exe -s --socks5-hostname 127.0.0.1:43866 https://www.cloudflare.com/cdn-cgi/trace   # Chrome 专用
curl.exe -s --proxy          http://127.0.0.1:43865 https://www.cloudflare.com/cdn-cgi/trace   # Claude Code
curl.exe -s --proxy          http://127.0.0.1:43867 https://www.cloudflare.com/cdn-cgi/trace   # Desktop
```

本机实测四种走法返回值完全一致：

| 入口 | ip | loc | colo | warp |
|---|---|---|---|---|
| TUN 全局 | <出口IP> | US | EWR | off |
| Code (43865) | <出口IP> | US | EWR | off |
| Chrome (43866) | <出口IP> | US | EWR | off |
| Desktop (43867) | <出口IP> | US | EWR | off |

`Check-ClaudeIp.ps1` 的判据：
1. 每个入口都能拿到 `ip=` 且 `loc=US`；
2. 四个入口的 `ip` 与 `loc` **必须完全相同**（有一个不同 → `FAIL`，说明某条入口绕开了代理组）；
3. `claude.ai` 的 trace 同样跑一遍（证明请求确实经过 Cloudflare，而不是被劫持到别处）。

> 只看 `ip` 还不够——`ip` 相同但 `loc` 不同意味着出口 IP 的地理归属被换了。
> 用 `https://ipinfo.io/<IP>/json` 交叉验证 ISP / ASN / 城市。

### 3.2 iprisk.top（唯一能自动出结论的信誉站）

**① 徽章接口（最省事）**

```
GET https://iprisk.top/badge/<IP>
```

返回约 1.1 KB SVG。分数藏在两个地方，**两个都要看**：

- `aria-label="<IP>: 95/100"`
- 文本节点 `<score>/100 低风险`

坑：`1.1.1.1` 的徽章 `aria-label` 有值而文本为空；`8.8.8.8` 反过来。所以解析必须是"先 aria-label，空则取文本"。

**② 详情页（拿完整画像）**

```
GET https://iprisk.top/ip/<IP>      → 约 62 KB 服务端渲染 HTML（可取）
GET https://iprisk.top/api/check    → 403
GET https://iprisk.top/api/myip     → 可用
```

页面里有两张表：

- **表一（多源一致性）**：每行 6 个 `<td>` = `来源 | 国家 | 地区 | 城市 | 坐标 | 时区`，来源固定 5 家（ip-api.com / ipinfo.io / IP2Location / proxycheck / ipapi.is）。用来判断"各库说法是否一致"。
- **表二（核心 key/value）**：用 `<table> → <tr> → <td>` 取成 dict 最稳。字段与实测值示例：

| key | 示例值 |
|---|---|
| IP 地址 | <出口IP> |
| 纯净度评分 | 95/100 |
| 风险信号等级 | 信号较少 |
| IP 类型 | 住宅 / 多源 ISP |
| 国家 / 州省 / 城市 | United States / New York / New York City · 中等可信 · 3/5 个有效来源一致 |
| 邮政编码 / 时区 / 参考坐标 | 10013 / America/New_York / 40.73, -74.08 |
| ISP / ASN | AviationAI / AS7922 |
| 是否代理/VPN / 代理类型 | 否 / None |
| 是否机房 IP | 否 |
| 标签 | 新IP&lt;3月, 优质纯净节点 |
| 最近检测时间 | 2026-09-13 13:34:56 |

其它可解析的选择器：

- 检查项：`<div class="checklist-item pass|fail">` 里的 `<span class="checklist-text">…</span>`
- 风险标签：`<div class="risk-chip-list"><span>…</span></div>`

> **注意**：字段名带空格/斜杠，键匹配要用通配（见 `Common.ps1` 的 `Get-DictValue`），
> 例如 `是否代理*`、`*代理/VPN*`、`*机房 IP*`。

**判据**（`Check-IpReputation.ps1`）：

| 项 | PASS | WARN | FAIL |
|---|---|---|---|
| 纯净度评分 | ≥ 90 | 70–89 | &lt; 70 |
| IP 类型 | 含"住宅"或"ISP" | 其它 | 含"机房/IDC/云" |
| 是否代理/VPN | 否 | — | 是 |
| 是否机房 IP | 否 | — | 是 |
| 检查项 | 全 pass | 存在 fail 项（如"IP 使用时间较短"） | — |
| 标签 | 能取到 | — | — |

阈值都在 `config/Topology.psd1` 的 `Thresholds` 节里，改阈值不用改代码。

### 3.3 ping0.cc（无头 Chrome 真实渲染）

渲染取数用 `Invoke-HeadlessDomFetch`，拿到 `Dom`（原始 HTML）与 `Plain`（去标签折叠后的纯文本）**两套**，
按字段性质分别取 —— 这是本轮踩出来的最关键经验：

| 字段 | 从哪取 | 正则 | 实测值 |
|---|---|---|---|
| 风控值 | DOM（风险条结构） | `(?s)riskcurrent.{0,400}?<span class="value">\s*([^<]*)</span>` | `9%` |
| 等级标签 | DOM（风险条结构） | `(?s)riskcurrent.{0,400}?<span class="lab">\s*([^<]*)</span>` | `极度纯净` |
| IP 类型 | **Plain** | `IP 类型 \(说明\?\)\s*(\S+(?: \S+)?)` | `家庭宽带 IP` |
| 原生 IP | **Plain** | `原生 IP \(说明\?\)\s*(非原生 IP\|广播 IP\|原生 IP)` | `原生 IP` |
| 共享人数 | DOM（属性） | `usecount="([^"]*)"` | `1 - 10 (极好)` |
| ASN 摘要 | DOM（meta） | `<meta name="description" content="([^"]*)"` | `<出口IP>-7922-Comcast…` |

**为什么「IP 类型」必须走 Plain 而不能走 DOM**：页面为了让用户看懂，在 `title` / 提示文案里
写了一大段解释，其中**包含 `IDC机房IP` 这个反例词**。在原始 HTML 上做正向匹配会先命中那段说明文字，
于是"家庭宽带 IP"被误判成"IDC机房IP" —— 同样的坑在 `ip.net.coffee` 的 `Trust Score` 上也出现过（DOM 上误匹配成 `6`）。

> **通用原则**：要"人眼看到的最终值" → 用 `ConvertTo-PlainText` 的输出；
> 只在取 HTML 属性（`usecount=`）或需要 HTML 结构（`riskcurrent` + `<span class="value">`）时才用 DOM。

### 3.4 ip.net.coffee/claude/（无头 Chrome 真实渲染）

同一个 `Invoke-HeadlessDomFetch`，但因为该页是 SPA，**必须给 `--virtual-time-budget`**，
否则拿到的只是 5 秒时的半成品页。取数全部走 `Plain`：

| 字段 | 正则 | 实测值 |
|---|---|---|
| Claude 专向出口 IP | `Claude AI出口IP\s*((?:\d{1,3}\.){3}\d{1,3})` | `<出口IP>` |
| 地理 | `Claude AI出口IP\s*(?:\d{1,3}\.){3}\d{1,3}\s*(.+?)\s*Claude AI信任评分` | `United States Texas Dallas Comcast Cable` |
| Trust Score | `信任评分\(Trust Score\)\s*(\d{1,3})` | `100` |
| IP 属性 | `IP 属性\s*(家庭住宅IP\|住宅IP\|机房IP\|数据中心IP\|IDC)` | `家庭住宅IP` |
| 风险信号 | `VPN\s*(未检测到\|检测到)` / `代理 \(Proxy\)\s*…` / `Tor\s*…` / `机器人 \(Crawler\)\s*(是\|否)` | 四项全"未检测到 / 否" |
| 滥用记录 | `滥用记录\s*(无记录\|有记录)` | `无记录` |
| 支持地区 | `Claude支持地区\s*(正常\|异常\|不支持)` | `正常` |

**两个必须知道的坑**：

1. **必须锚定 `Claude AI` 前缀**。同一个页面上还有一个 `Cloudflare 出口IP`，走的是非 Claude 域名那条路
   （订阅兜底组 / 直连，随订阅而变）。裸匹配 `出口IP` 会抓到它，得出"出口不是 ACCOUNT-US"的假结论。
2. **必须排除 `未检测到` 里的 `检测到`**。判"有没有风险信号"时若写 `-match '检测到$'`，
   干净的页也会被判成脏 —— 正确写法是 `($_ -match '检测到') -and ($_ -notmatch '未检测到')`。

**这条顺带解决了一个安全疑点**：coffee 页报的 `Claude AI出口IP` 与 `Cloudflare 出口IP` 是两个不同的 IP，
前者才是 ACCOUNT-US 的出口，说明**无头 Chrome 与手工浏览走的是同一套域名规则**，
自动化取数与人工看的结果一致，可以放心用。

### 3.5 无头 Chrome 真实渲染的硬性要求（三条，缺一不可）

```
chrome.exe --headless=new --disable-gpu --no-first-run
  --disable-extensions --disable-default-apps --mute-audio
  --window-size=1280,2400
  --disable-blink-features=AutomationControlled
  --user-agent="Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/<真实主版本>.0.0.0 Safari/537.36"
  --user-data-dir="<每次新建的独立临时目录>"
  --timeout=30000 --virtual-time-budget=8000
  --dump-dom "<url>"
```

| # | 要求 | 不给会怎样 |
|---|---|---|
| 1 | **真实 UA**（主版本从本机 `chrome.exe` 的 `ProductVersion` 现取） | ping0.cc 返回 **41 字节空页** |
| 2 | **独立 `--user-data-dir`** | Chrome 把 URL 转交给用户正在用的实例后自己立刻退出，`--dump-dom` 什么都拿不到 |
| 3 | **`--virtual-time-budget`** | SPA（ip.net.coffee）只拿到 5 秒时的半成品页；8000ms 是实测"数据完整 + 用时最短"的点 |

实测耗时：ping0 约 10s、ip.net.coffee 约 11s；两块加起来会让全量总检从 ~47s 涨到 ~68s。

还有一个**纯工程坑**（不是站点问题）：别用 `Start-Process -RedirectStandardOutput` 接 DOM ——
输出文件句柄在父进程里还占着，紧接着读会得到 **0 字节**。要用
`[System.Diagnostics.ProcessStartInfo]` + `RedirectStandardOutput` + **先 `ReadToEndAsync()` 再 `WaitForExit()`**
直读管道（顺序反了，12 万字节的 DOM 会把管道堵死造成死锁）。

## 4. 人工交接怎么做

`Check-IpReputation.ps1` / `Check-ClaudeIp.ps1` 结尾会打印一份**浏览器交叉复核清单**，
加 `-OpenBrowser` 时还会**自动在专用 Chrome 里打开对应页面**
（`Open-HandoffPage`，复用同一个 UserData 目录，不污染日常浏览器）。

清单现在只有一条是**必看**，其余是**选做**：

| 必要度 | 站点 | 为什么 |
|---|---|---|
| **必看** | `ippure.com` | 接口要混淆 JS 现算的 `x-t` 签名头，无头拿不到 → 只能人眼 |
| 选做 | `iprisk.top` | 无头已读到分数与信号；人眼是防"站点改版导致正则失配" |
| 选做 | `ip.net.coffee/claude/` | 无头已读到 Trust Score / 属性 / 风险信号；人眼多看"时区与语言是否自洽" |

`ippure.com` 看什么：人机流量占比 human ≥ 85%；IP 来源属性 = 住宅 / 原生；系数 0%。

> 三个标签页留着别关：`ping0.cc` / `ippure.com` / `iprisk.top`（换节点后可刷新复看）。

## 5. 换订阅 / 换节点之后要跑什么

这是最常被问的问题。答案是**只跑检测，不动配置**：

```powershell
# 换完订阅、选好节点后
pwsh -File scripts\checks\Check-IpReputation.ps1     # 自动部分
pwsh -File scripts\checks\Check-ClaudeIp.ps1         # 逐入口 trace + 人工清单
```

**不需要**改脚本、不需要重新导入订阅、不需要动 `settings.json`。

原理：全局扩展脚本 `Clash全局账号通道.js` 里的 `ACCOUNT-US` 组用的是 `include-all-proxies: true`，
所以**任何新订阅的节点都会自动进入这个组**，端口、规则、DNS 分层全部复用。

唯一例外见 `03-变更与回滚SOP.md` 的 SOP-4（新增第三个账号/浏览器时）。

## 6. 合格线速查

| 指标 | 合格线 | 谁判 |
|---|---|---|
| 出口 IP 在四个入口是否一致 | 完全一致 | 自动 |
| `loc` 是否 US | 必须 US | 自动 |
| iprisk 纯净度评分 | ≥ 90（70–89 为 WARN；本机基线 95） | 自动 |
| iprisk 是否代理 / 是否机房 | 均为"否" | 自动 |
| ping0 风控值 | &lt; 20%（本机基线 9%） | **自动** |
| ping0 IP 类型 | `家庭宽带 IP` | **自动** |
| ping0 原生 IP | `原生 IP` | **自动** |
| coffee Trust Score | ≥ 80（本机基线 100） | **自动** |
| coffee IP 属性 | `家庭住宅IP` | **自动** |
| coffee 风险信号 | VPN / Proxy / Tor / Crawler 全"未检测到 / 否" | **自动** |
| coffee 滥用记录 | `无记录` | **自动** |
| coffee 支持地区 | `正常` | **自动** |
| ippure 人机占比 | human ≥ 85% | 人工（必看） |
| ippure 来源属性 | 住宅 / 原生；系数 0% | 人工（必看） |

新增阈值都在 `config/Topology.psd1`：`Thresholds.Ping0RiskPass` / `Ping0WantIpType` /
`CoffeeTrustPass` / `CoffeeWantAttr` / `IppureFactorPass` / `IppureHumanWarn`。改阈值不用改代码。
