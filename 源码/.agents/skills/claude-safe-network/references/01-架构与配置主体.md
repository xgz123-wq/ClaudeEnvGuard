# 架构与配置主体

## 1. 一张分层图

```
【用户可见层】
  桌面 5 个 Claude 相关 .lnk（3 个脚本类由 pwsh 7 拉起、2 个浏览器类由 Chrome 拉起）
      ↓
【应用入口层】  三个端口
  43865  Claude Code      HTTP   ← ~/.claude/settings.json 的 env 代理
  43866  专用 Chrome      SOCKS5 ← .lnk 的 --proxy-server=socks5://127.0.0.1:43866
  43867  Claude Desktop   HTTP   ← HKLM Policy egressProxyUrl / configLibrary
      ↓
【代理引擎层】  Clash Verge Rev (mihomo v1.19.29), TUN + rule 模式
  全局扩展脚本 Script.js  ← 整套配置的真正主体
      ↓
【出口层】  ACCOUNT-US 代理组 → 美国住宅 VPS 出口 <出口IP>
      ↓
【系统兜底层】  WFP 8 条精确阻断（防 4 个 Claude 程序绕开代理直连）
```

## 2. 配置主体 = 全局扩展脚本 `Script.js`

**路径**：`%APPDATA%\io.github.clash-verge-rev.clash-verge-rev\profiles\Script.js`

### 为什么它是「主体」而不是订阅

`profiles.yaml` 顶层有两条**全局**条目：

```yaml
- uid: Merge
  type: merge
  file: Merge.yaml
- uid: Script
  type: script
  file: Script.js
```

它们**没有 `option:` 字段**，区别于 `profiles:` 数组里每个订阅（那些带 `option:` 指向 per-profile 的 patch 文件）。
→ **结论：全局扩展脚本对所有订阅生效，换订阅不用改一行。**

旁证：任取一个订阅，其 `selected` 里都能看到全局脚本注入的 `ACCOUNT-US`。

### `Script.js` 的六步职责

| # | 做什么 | 关键实现 | 为什么这样设计 |
|---|---|---|---|
| ① | **重建 `ACCOUNT-US` 组** | 先 filter 掉同名，再 `unshift` `{name:"ACCOUNT-US", type:"select", "include-all-proxies": true, "exclude-type": "Direct\|Reject"}` | `include-all-proxies: true` 让它**自动吃下任何新订阅的节点**，无需改脚本 |
| ② | **Claude 专属 DNS 分层** | 给 12 个 Claude 域名前缀写 `dns.nameserver-policy = ["https://1.1.1.1/dns-query#ACCOUNT-US", "https://8.8.8.8/dns-query#ACCOUNT-US"]` | 只加固 Claude 链路；**明确不覆盖** `nameserver` / `direct-nameserver` / `fallback`，避免 09-10「全局 DNS 改到 ACCOUNT-US 导致飞书等国内应用断网」事故复发 |
| ③ | **TUN 防旁路** | `config.tun["strict-route"] = true`、`config.tun["dns-hijack"] = ["any:53","tcp://any:53"]` | 堵「多网卡 DNS 旁路」根因（09-10 定位）。这解释了为何运行时 `strict-route=True` 而静态 `config.yaml` 里写 `false` |
| ④ | **注入两个 listener** | `account-us-socks` (socks, `127.0.0.1:43866`, `udp:false`) 与 `claude-desktop-http` (http, `127.0.0.1:43867`, `proxy:"ACCOUNT-US"`) | 43866/43867 的来源。这也是运行时 `socks-port=0` / `port=0` 仍能用的原因 |
| ⑤ | **规则清理与置顶（幂等）** | 先清理旧受管规则和订阅注入的 `DST-PORT,25/110/143/465/587/993/995,DIRECT`，再置顶 Claude / DoH 规则 | 邮件流量不再无条件直连，而是继续按后续 `GEOSITE/GEOIP/MATCH` 分流；`inboundRule` 让 43866 流量强制归组 |
| ⑥ | **`geox-url.asn` 兜底** | 指向 `gh-proxy.com` 镜像的 `GeoLite2-ASN.mmdb` | 默认源在 GitHub releases，墙内拉取失败会导致**整份配置加载失败** |

### 置顶规则包含什么

- 12 个 Claude / Anthropic 域名 matcher，各拼 `,ACCOUNT-US`（anthropic.com / claude.ai / claude.com / claude.app / clau.de / claudemcpclient.com / claudemcpcontent.com / claudeusercontent.com / `anthropic.auth0.com` / `servd-anthropic-website.b-cdn.net` / `anthropic.com.cdn.cloudflare.net` / `anthropic-com.ghost.io`）。遥测类域名（sentry / statsig / datadog / sift / intercom / usefathom）**明确不入组**，原因见第 3 节
- `IP-CIDR,160.79.104.0/21,ACCOUNT-US,no-resolve`
- `IP-CIDR6,2607:6bc0::/32,ACCOUNT-US,no-resolve`
- `IP-ASN,399358,ACCOUNT-US,no-resolve`（Anthropic 自有 ASN）
- `DOMAIN-SUFFIX,cloudflare-dns.com` / `DOMAIN-SUFFIX,dns.google` → `DIRECT`（2026-09-28 加固：DoH 走 443 不受 53 劫持，避免落兜底规则进美国线路把国内域名解析成海外 IP）

> 这就是「TUN 关掉 Claude 就连不上」的原因：Claude 相关流量被**规则**强制指向 ACCOUNT-US，而 ACCOUNT-US 是走的代理。

## 3. per-profile 覆写：不是必需项

**本套不需要订阅级 rules 覆写。** Claude 的组、置顶规则、listener、DNS policy 全部由全局 `Script.js` 注入，与订阅解耦。

历史上曾经把一套 Claude 规则（25 条）写进某个订阅自己的 per-profile 覆写文件，后来废弃了 —— 原因是那套规则指向订阅特有的组名，**换订阅就会静默失效**。改由全局脚本统一注入后，这个耦合消失。

若某个订阅的 per-profile 文件里还留着 `delete:` 补丁，它的作用只是删除该订阅自带的原规则，与 Claude 链路无关；换订阅后**不需要**补写或跟改，留着也无害。

→ **换订阅后要复核这一条 `delete` 是否仍指向存在的目标**，否则就是无效补丁（无害但不干净）。

## 4. Claude Code 侧配置

`~/.claude/settings.json` 的 `env` 字段实现**进程级**代理，等价于外部 Proxifier 方案，
**不需要装 Proxifier**：

- `ALL_PROXY` / `HTTPS_PROXY` / `HTTP_PROXY` = `http://127.0.0.1:43865`
- `NO_PROXY` = `localhost,127.0.0.1,*.local`
- `BROWSER` = `noop-browser.bat`

**官方限制**：Claude Code **只支持 HTTP/HTTPS 代理，不支持 SOCKS**
（事实来源：code.claude.com 官方文档；本分享版不含该文档的转引存档，需要时请直连官方文档核对）。
→ 所以 Code 用 43865（http），Chrome 才能用 43866（socks5）。

## 5. Claude Desktop 侧配置（最能翻车的一块）

MSIX 包（不可改安装目录），三个关键事实：

1. **只认官方字段** `configLibrary.egressProxyUrl`；**会拒绝** `--host-resolver-rules` 等 Chromium 参数。
   - 策略层：`HKLM\SOFTWARE\Policies\Claude` → `egressProxyUrl = http://127.0.0.1:43867`
   - 本地库：`%LOCALAPPDATA%\Claude-3p\configLibrary\`，由 `_meta.json` 的 `appliedId` 指向实际 profile 文件
2. **`disableAutoUpdates` 必须与 `egressProxyUrl` 写在同注册表层**，否则 Desktop 会**忽略代理、回退直连**。这是 09-12 踩出来的。
   - 注意 `HKLM\SOFTWARE\WOW6432Node\Policies\Claude` 是**冗余镜像副本**，因为 `SOFTWARE\Policies` 在 Windows 上不受 WOW64 重定向，32/64 位读到同一路径。
3. **Desktop 未禁用 WebRTC**，靠 WFP 精确规则堵非回环直连；**每次 Desktop 或 VS Code Claude Code 插件升级换路径都必须重新核验对应规则**。

## 6. 系统兜底层：WFP 精确阻断

- 位置：`scripts\desktop\维护文件\`（本 skill 内，自包含）
  - `应用直连过滤.cs`（26KB，WFP 实现，P/Invoke）
  - `应用直连防护管理.ps1`（8.3KB，安装 / Verify / 卸载）
  - `应用过滤目标.json`（防篡改清单）
- 机制：**WFP filter**（`FwpmFilterAdd0`），层 = `ALE_AUTH_CONNECT_V4` / `V6`，
  条件 = `FWPM_CONDITION_ALE_APP_ID`（精确到 exe 路径）**AND** `FWPM_CONDITION_FLAGS` 带非回环。
  动作 = **Block**。因此：
  - 只有名单里那 4 个 `claude.exe` 受影响：Desktop、两个 CLI 路径、VS Code 插件内置程序；不阻断整个 `Code.exe`；
  - `claude-network-probe.exe` 不在名单 → 它测出 `stunUdp4.ok=true` / `directTcp4=connected` 属**预期**，**不是泄漏**；
  - `Get-NetFirewallRule` **查不到**它们（不同机制），别用 Windows 防火墙工具去验证。
- **安装与 Verify 都需要管理员**。非提权跑 Verify 会得到 `0x00000005` = `ERROR_ACCESS_DENIED`。
